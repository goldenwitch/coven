# Gemini Tool Calling

> **Status**: Draft  
> **Created**: 2026-02-09

---

## Summary

Add tool calling support to the Gemini agent leaf. The Gemini request gateway detects `functionCall` parts in responses, writes provider-specific tool use entries, waits for results, and re-sends with `functionResponse` parts — matching the pattern established by the Claude agent.

---

## Motivation

Claude's request gateway already implements the full tool-call loop (detect tool_use, write journal entry, wait for result, re-send). Gemini and OpenAI lack this entirely. Until all agent leaves support tool calling, companion libraries like `Coven.Agents.FileSystem` only work with Claude.

Gemini uses `functionCall` / `functionResponse` parts within its content structure, plus `tools` and `toolConfig` on the request. The Gemini wire types in `Coven.Gemini.Client` currently have no tool-related fields.

---

## Design

### Wire Type Additions

`GeminiPart` gains two optional fields:

| Field | Type | Purpose |
|-------|------|---------|
| `FunctionCall` | object (name + args) | Present when Gemini requests a function call |
| `FunctionResponse` | object (name + response) | Sent back with the tool result |

`GeminiGenerateContentRequest` gains:

| Field | Type | Purpose |
|-------|------|---------|
| `Tools` | list of tool declarations | Function declarations for the model |
| `ToolConfig` | object | Optional: function calling mode (auto/any/none) |

A tool declaration contains `name`, `description`, and `parameters` (JSON Schema object).

### Entry Types

Two new entry types on `GeminiEntry`:

```
GeminiFunctionCall { sender, call-id, function-name, arguments-json, response-id, timestamp, model }
GeminiFunctionResponse { sender, call-id, function-name, result, is-error }
```

`call-id` is generated by the gateway to correlate calls with results. Gemini's API does not provide a built-in call ID — the gateway assigns one per function call part.

### Transmuter

`GeminiTransmuter` adds two mappings:

| Direction | From | To |
|-----------|------|----|
| Gemini → Agent | `GeminiFunctionCall` | `AgentToolCall` |
| Agent → Gemini | `AgentToolResult` | `GeminiFunctionResponse` |
| Agent → Gemini | `AgentToolFailure` | `GeminiFunctionResponse` (error) |

`AgentToolCall` already exists in `Coven.Agents`. The transmuter maps `call-id` ↔ `correlation-id`.

### Registration

`GeminiRegistration` gains `EnableTools()`, mirroring `ClaudeRegistration`. Returns `this` for fluent chaining.

### Gateway Tool Loop (Request)

`GeminiRequestGatewayConnection` changes:

1. Inject `IEnumerable<ToolDefinition>` via constructor
2. Convert `ToolDefinition` → Gemini tool declarations on the request
3. After response, scan candidate parts for `functionCall`
4. If found: write `GeminiFunctionCall` entries, wait for `GeminiFunctionResponse` via `WaitForAsync`
5. Append assistant content (with function call parts) and user content (with function response parts)
6. Re-send — loop until response contains no function calls

This mirrors Claude's `while(true)` loop with `ExtractToolUseBlocks` → wait → append → continue.

### Manifest

When `ToolsEnabled`, `GeminiCovenBuilderExtensions` adds:

- `AgentToolCall` to produces set
- `AgentToolResult` and `AgentToolFailure` to consumes set

### Virtual Gateway

`VirtualGeminiGateway` gains:

- `EnqueueToolCallResponse(functionName, argumentsJson, followUpContent)` — scripts a response containing a function call part, then expects a follow-up send after the tool result arrives
- `ScriptedGeminiToolCallResponse` scripting type — holds the function call and the final text response to emit after tool results
- On `SendAsync`: emit `GeminiFunctionCall` to journal, wait for `GeminiFunctionResponse`, then emit the final response

### Transcript Builder

`GeminiEntryToContentTransmuter` and `GeminiTranscriptBuilder` must handle `GeminiFunctionCall` and `GeminiFunctionResponse` entries when rebuilding conversation history, mapping them to the appropriate `functionCall` / `functionResponse` parts in `GeminiContent`.

## Scope

**In scope:**
- Wire type additions to `Coven.Gemini.Client` (function call/response parts, tools on request)
- `GeminiFunctionCall` and `GeminiFunctionResponse` entry types
- `GeminiTransmuter` tool call/result mappings
- `GeminiRegistration.EnableTools()`
- `GeminiRequestGatewayConnection` tool-call loop
- `GeminiCovenBuilderExtensions` manifest updates
- `VirtualGeminiGateway` tool call scripting
- `GeminiTranscriptBuilder` tool entry handling
- E2E test: Gemini tool call round-trip with FileSystem companion

**Out of scope:**
- Streaming gateway tool support (separate concern, follows same pattern later)
- Parallel tool execution within a turn
- New companion libraries
